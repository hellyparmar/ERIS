# Demo dataset

ERIS ships with a **synthetic** dataset for one fictional company, *Urban Harvest Supermarkets Pvt. Ltd.*, a
neighbourhood supermarket chain. Its catalogue is what a supermarket shelf carries: packaged groceries,
fresh produce, dairy, and household and personal care. It is generated by code (`api/app/seed/generator.py`, generator version **3.1.0**). It is
not collected from a real business, and the app says so wherever the data is shown: the System tab, report
"About" sheets, assistant provenance and invoice watermarks.

## Generating it

The dataset is created automatically the first time the API starts on an empty database. It can also be
regenerated from **Settings → System & data**, or from the command line:

```bash
cd api
python -m app.seed                                   # defaults: 730 days, 5 outlets, seed 42, ends yesterday
python -m app.seed --days 365 --outlets 7 --seed 7 --end-date 2026-03-31
```

The same options can be set with environment variables: `SEED_DAYS`, `SEED_OUTLETS`, `SEED_RANDOM_STATE` and
`SEED_END_DATE`. **The same seed and end date always produce the same data.**

Every run writes one `dataset_info` row recording the data source (`synthetic`), generator version, seed,
generation time, the period covered, the parameters and the row counts. Every synthetic bill references that
row (`sales.dataset_id`). Bills entered by hand have `source = "manual"`, and imported bills have
`source = "import"` plus `import_id`.

## How demand is simulated

Each bill is simulated individually.

**Bills per day per outlet** = base × outlet size × weekday factor × growth trend × season × festival effect ×
rain footfall × new-outlet ramp-up × noise × (injected anomaly)

**Products in a basket** come from popularity × product seasonality × temperature and rain response ×
promotion uplift × price elasticity. Companion items are then added, such as butter with bread, cola with
chips, milk with tea, or dishwash liquid with detergent.

| Effect | How it is modelled |
|---|---|
| Weekday | Mon 0.88 … Sat 1.24, Sun 1.16 |
| Trend | Per-outlet growth per year: +16% Koregaon Park, +12% Andheri West, -8% SG Highway (new competitor) |
| Festivals | Diwali, Holi, Ganesh Chaturthi, Navratri, Raksha Bandhan, Eid, Christmas and New Year, with build-up windows; festive categories spike about 3× before Diwali |
| Weather | City climatology (monsoon in Mumbai and Pune); rain reduces footfall (up to -30%) and increases delivery orders; heat lifts cold drinks, curd and ice cream; Diwali lifts gifting, dry fruits and cleaning supplies; salary-day stock-up of staples in the first days of the month |
| Promotions | Demand multiplier = (1 − discount)^−2.0 on promoted items; the line records list price, unit price and `promotion_id` |
| Price changes | Demand multiplier = (new / old price)^−1.0 |
| Stockouts | Random outages per outlet and product; the shopper takes a same-category substitute 60% of the time, otherwise the sale is lost |
| Customers | Loyalty strength, join dates and 22% churn, so RFM segments are meaningful |
| Payments | UPI share rises over time; cash, card and credit for business customers |

## Labelled anomalies (ground truth)

| Kind | Count | What was injected |
|---|---:|---|
| pos_outage | 7 | Most of a day's bills missing (billing system down) |
| bulk_order | 6 | One very large catering order |
| entry_error | 5 | A quantity typed with an extra "00" |
| local_event | 5 | Footfall boost from a nearby event |
| closure | 3 | Outlet closed for the day (no sales) |

The anomaly detector never reads these labels. They are used only to score it (precision, recall, F1); see the
Anomalies & drivers page, `docs/MODEL_CARD.md` and the notebook.

## Invalid sample rows

The importer's validation is demonstrated with generated sample files: **Data import → Sample with mistakes**
(`GET /api/imports/samples/{kind}?with_errors=true`). The sales sample contains an unknown SKU, a negative
quantity, an impossible date, an unknown outlet, an unsupported payment method and an invalid phone number.
These are built from the database's real outlets and products, so the valid rows import cleanly.

## Keeping the demo current

When the API starts on a demo database whose data has gone stale (for example, the project was opened months
later), it shifts every date forward so the history ends yesterday. This applies only when the database
contains nothing but synthetic data. Real or imported data is never moved.

## Limitations

- The demand model is hand-built from plausible retail patterns and public climate normals. It is not fitted
  to any real retailer, so model accuracy on this data says nothing definitive about accuracy on real data.
- Weather is synthetic: it is drawn from city climatology, not from historical observations.
- Customers, suppliers, addresses, phone numbers and GSTINs are fictional.
