# Demo dataset

ERIS ships with a **synthetic** dataset for one fictional company, *Saffron Table Restaurants Pvt. Ltd.*, a
casual-dining restaurant chain. Its menu is North Indian and Indo-Chinese food with soups, desserts and drinks; its
kitchens stock the ingredients those dishes are made from, and every dish has a recipe. It is generated by code
(`api/app/seed/generator.py`, generator version **4.0.0**). It is not collected from a real business, and the app
says so wherever the data is shown: the System tab, report "About" sheets, assistant provenance and invoice
watermarks.

## Generating it

The dataset is created automatically the first time the API starts on an empty database. It can also be
regenerated from **Settings → System & data**, or from the command line:

```bash
cd api
python -m app.seed                                   # defaults: 730 days, 5 outlets, seed 42, ends yesterday
python -m app.seed --days 365 --outlets 7 --seed 7 --end-date 2026-03-31
```

The same options can be set with environment variables: `SEED_DAYS`, `SEED_OUTLETS`, `SEED_RANDOM_STATE` and
`SEED_END_DATE`. **The same seed and end date always produce the same data.**

Every run writes one `dataset_info` row recording the data source (`synthetic`), generator version, seed,
generation time, the period covered, the parameters and the row counts. Every synthetic bill references that
row (`sales.dataset_id`). Bills entered by hand have `source = "manual"`, and imported bills have
`source = "import"` plus `import_id`.

## How demand is simulated

Each bill is simulated individually.

**Bills per day per restaurant** = base × outlet size × weekday factor × growth trend × season × festival effect ×
rain × new-outlet ramp-up × noise × (injected anomaly)

**Each bill** gets a channel (dine-in, takeaway or delivery, with each restaurant's own delivery share, pushed up by
rain) and a party size (covers: about 2.7 guests at a dine-in table, more at weekends). Company orders are larger and
concentrate on a few dishes per course, in bulk.
The party then orders **by course**: mains (about 0.7 per guest), breads or a rice side with curries, starters,
soups, drinks and desserts, each with its own probability per channel. Within a course, dishes are chosen by
popularity × seasonality × temperature and rain response × promotion uplift × price elasticity × the restaurant's
appetite for non-vegetarian food.

| Effect | How it is modelled |
|---|---|
| Weekday | Mon 0.80, Tue 0.78 … Sat 1.42, Sun 1.34 |
| Time of day | Lunch peak 12-15h, larger dinner peak 19-22h; delivery runs later into the night |
| Trend | Per-outlet growth per year: +16% Koregaon Park, +12% Andheri West, -8% SG Highway (new competitor) |
| Festivals | Fewer guests on Diwali night and Holi, get-togethers after Diwali, New Year's Eve (×1.75), Christmas, Valentine's Day, Eid; sweets sell more around festivals |
| Non-vegetarian food | Outlet appetite (SG Highway in Ahmedabad sells less than half the chain average); dips in Navratri (×0.55), Shravan and Ganesh Chaturthi, rises at Eid |
| Weather | City climatology (monsoon in Mumbai and Pune); rain lowers dine-in footfall and shifts orders to delivery; hot days sell lassi, soft drinks and ice cream; rainy days sell pakoras, chai and manchurian; winter sells soups, halwa and coffee |
| Promotions | Demand multiplier = (1 − discount)^−2.0 on promoted dishes; the line records list price, unit price and `promotion_id` |
| Price changes | Demand multiplier = (new / old menu price)^−1.0 |
| Ingredient outages | Random outages per restaurant of specialty ingredients (meat, fish, paneer and cream most often); staples used in more than 8 dishes (onion, oil, masala, flour...) never run out. Every dish needing the ingredient is off the menu for the day; the guest takes a similar dish 60% of the time, otherwise the order is lost |
| Food cost | Recipe quantities × the day's ingredient costs, so tomato and onion price spikes show up in margins |
| Customers | Loyalty strength, join dates and 25% churn, so RFM segments are meaningful |
| Payments | UPI share rises over time; delivery orders are paid online (UPI or card); company accounts on credit |

## Labelled anomalies (ground truth)

| Kind | Count | What was injected |
|---|---:|---|
| pos_outage | 7 | Most of a day's bills missing (billing system down) |
| bulk_order | 6 | One very large corporate party order (biryani, curries, naan) |
| entry_error | 5 | A quantity typed with an extra "00" |
| local_event | 5 | Footfall boost from a concert or match nearby |
| closure | 3 | Restaurant closed for the day (kitchen maintenance) |

The anomaly detector never reads these labels. They are used only to score it (precision, recall, F1); see the
Anomalies & drivers page, `docs/MODEL_CARD.md` and the notebook.

## Invalid sample rows

The importer's validation is demonstrated with generated sample files: **Data import → Sample with mistakes**
(`GET /api/imports/samples/{kind}?with_errors=true`). The sales sample contains an unknown dish code, a negative
quantity, an impossible date, an unknown outlet, an unsupported payment method and an invalid phone number.
These are built from the database's real outlets and menu, so the valid rows import cleanly.

## Keeping the demo current

When the API starts on a demo database whose data has gone stale (for example, the project was opened months
later), it shifts every date forward so the history ends yesterday. This applies only when the database
contains nothing but synthetic data. Real or imported data is never moved.

The move rewrites every dated row, which takes minutes on a very small server and replaces the answers stored in the
build. The hosted demo therefore sets `DEMO_SHIFT_DATES=false`: it keeps the dates it was built with, answers
relative to the last day of data, and each deploy refreshes the data.

## Limitations

- The demand model is hand-built from plausible restaurant patterns and public climate normals. It is not fitted
  to any real restaurant, so model accuracy on this data says nothing definitive about accuracy on real data.
- Weather is synthetic: it is drawn from city climatology, not from historical observations.
- Customers, suppliers, addresses, phone numbers and GSTINs are fictional. Recipes and costs are plausible
  estimates, not a real kitchen's specifications.
